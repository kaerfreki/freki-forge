Measured on **2026-10-06**:

- GPU: NVIDIA GeForce RTX 4080, 16376 MiB (Windows driver 617.14, WDDM; ~1.1–1.7 GiB already used by the desktop)
- RAM: 32 GB · OS: Windows 11
- llama.cpp `b10590` (commit `6657ded4f`), official Windows CUDA 13.3 build
- Model: [`unsloth/Qwen3.8-27B-GGUF`](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF) (27.32 B params, dense)

This is a different OS and runtime from the Ollama / vLLM tables
([`RESULTS.md`](RESULTS.md), [`RESULTS-vllm.md`](RESULTS-vllm.md)), so
compare trends, not absolute numbers. It answers one question: **which
quant of a 27B dense model is usable on a 16 GB card?**

## `llama-server` in practice (`UD-IQ4_XS`, `--flash-attn on`, KV cache `q8_0`, 32k context)

| Configuration | VRAM used | Generation |
| --- | ---: | ---: |
| Text only, all layers on GPU, `--parallel 1` | 15113 MiB | **41.6 tok/s** |
| + vision projector (`mmproj-F16`), `--fit on`, `--parallel 1` | 15630 MiB | 15.3–16.1 tok/s |
| + vision projector, `-ngl 999`, default 4 slots | 15798 MiB | 21.9–22.2 tok/s |

With the vision projector loaded, prompt processing on image prompts
(2,110–3,666 tokens) ran at 687–858 tok/s with `--fit on` versus 61–71 tok/s
in the overcommitted 4-slot configuration. Single requests, not medians.

## Takeaways

- **`UD-IQ4_XS` is the sweet spot on 16 GB**: 4-bit weights at roughly
  2-bit speed (42 vs 45 tok/s generation) and faster prefill than `Q2_K_XL`.
- `Q4_K_M` (15.3 GiB) and anything larger does not fit alongside a KV cache;
  partial offload drops generation to 8–14 tok/s.
- Adding the vision projector pushes IQ4_XS past 16 GB. Let `--fit on`
  move a few layers to the CPU (≈15 tok/s). Setting `-ngl 999` disables
  `--fit` and overcommits VRAM.
- Keep `--parallel 1` on a single-user box: each extra slot reserves its own
  KV cache.

## Method / caveats

- `llama-bench -fa 1 -p 512,4096 -n 128 -r 2 -o md` for full offload;
  `-p 512 -n 64 -r 1` with an `-ngl` sweep for partial offload. Only 1–2
  repetitions, so these are less robust than the 3-run medians elsewhere in
  this repo.
- Other GPU work (model downloads, a browser) was running on the host
  during parts of the session; VRAM figures include the desktop baseline.
- The `llama-server` rows are single requests through the
  OpenAI-compatible API (`timings.predicted_per_second`), thinking disabled.
  The 41.6 tok/s row used a short prompt, so its prompt rate (165 tok/s)
  is not representative and is omitted.
